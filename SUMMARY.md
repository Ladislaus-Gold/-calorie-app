## 1. Что это и как устроено

**Health** — PWA (устанавливается на экран «Домой» iPhone, iOS 26): дневник питания, вода и напитки, кофеин, физические нагрузки, личный план, отчёты, **план домашних тренировок (v95, раздел 12)**, анализ через Google Gemini и **автоматическая выгрузка данных Apple Watch / Здоровья (шаги, пульс, тренировки)**, см. раздел 11.

| Слой | Решение |
|---|---|
| Хостинг | GitHub Pages (статические файлы, без сборки) |
| Вход | Firebase Authentication, Google (popup, запасной redirect) |
| База | Cloud Firestore, офлайн-кэш `persistentLocalCache` (несколько вкладок) |
| Firebase SDK | Web SDK 13.0.0 с gstatic (app, auth, firestore), ES-модули |
| Firebase-проект | `calorie-app-45bd1` |
| Данные о продуктах | Open Food Facts (лицензия ODbL), собственный стартовый набор |
| ИИ-анализ | Google Gemini API напрямую из браузера, ключ хранится только на телефоне |
| Данные Apple Watch | Health Auto Export (iPhone) → Cloudflare Worker `health-ingest` → Firestore (раздел 11) |
| Supabase | не используется: он занят другим приложением (Accounting), поэтому выбран Firebase |

Приложение — один HTML и три ES-модуля, без npm и без сборки. Обновление = загрузка файлов в репозиторий через GitHub (Add file → Upload files).

## 3. Модель данных в Firestore

```
products/{id}                      общая база продуктов (видят все вошедшие)
drinkdb/{id}                       общая база напитков (v102; видят все вошедшие, менять может автор)
barcodes/{код}                     штрих-коды других упаковок продукта (v51): productId, createdBy, createdAt; видят и используют все вошедшие
users/{uid}/entries/{id}           записи дневника
users/{uid}/water/{id}             вода (документ на день)
users/{uid}/activity/{id}          нагрузки
users/{uid}/drinks/{id}            напитки без калорий
users/{uid}/settings/profile       профиль, план, цель по калориям, mealSplit (распределение по приёмам пищи, %)
users/{uid}/settings/drinks        избранные напитки (fav)
users/{uid}/settings/ai            последний ответ ИИ: text, ts, model, from, to (v24)
users/{uid}/weights/{ГГГГ-ММ-ДД}   вес на день (v54): date, kg, updatedAt
users/{uid}/settings/training      анкета тренировок (v95): place, days, equip, minutes, level, limits, dumbbellKg, bandKg (вес резинки по цвету, v97), startedAt, moves, updatedAt
users/{uid}/trainlog/{ГГГГ-ММ-ДД}  отметки плана (v95): date, done{"группа:упражнение":true}, minutes; с v97 ещё finished, finishedAt, feel (1–5), used[], bands{цвет:кг}, dumbbellKg, plan[]; вне workouts/activity, в статистику не входит
users/{uid}/health/{ГГГГ-ММ-ДД}    итоги дня из Apple Health (v29): steps, activeKcal, hrAvg, hrMin, hrMax, hrN, restingHr, updatedAt
users/{uid}/workouts/{id}          тренировки с Apple Watch (v29): name, date, start, end, minutes, kcal, distanceKm, hrAvg, hrMax, hrMin, indoor, strength, updatedAt
```

**products** — поля: `name`, `brand`, `barcode`, `kcal`, `protein`, `fat`, `carbs` (значения на 100 г), `source`, `createdBy`, `createdByName`, `createdAt`, `updatedAt`, опционально `drink` (bool), `hydrationPct`, `caffeineMg100`.

**entries** — `date` (YYYY-MM-DD), `meal` (breakfast/lunch/dinner/snack), `name`, `grams`, `kcal`, `protein`, `fat`, `carbs`, `createdAt`; у напитков и супов дополнительно `drink: {pct, caf100}` (гидратация % и кофеин на 100 мл).

**health** и **workouts** пишет только Cloudflare Worker (через сервисный аккаунт, в обход правил); приложение их читает и в `workouts` меняет единственное поле `strength` (кнопка «Отметить силовой»). Подробнее о полях в разделе 11.

**water** — `{date, ml}`, изменяется через `increment`. **activity** — `{date, type, name, minutes, kcal, createdAt}`. **drinks** — `{date, drinkId, name, ml, pct, caf100, alc?, createdAt}`.

**Правила доступа (firestore.rules):**
- `users/{uid}/**` — читает и пишет только владелец.
- `products` — читают все вошедшие; создавать может любой (проверка `validProduct`: набор полей, типы, пределы: kcal 0–1000, БЖУ 0–100, hydrationPct −400…200, кофеин 0–1000); **менять и удалять может только автор** (`createdBy == uid`).
- `drinkdb` (v102) — читают все вошедшие; создавать может любой (`validDrink`: n 1–120 символов, h −400…200, c 0–2400, k 0–1000, p/f/cb 0–100, bc ≤12 кодов, `createdBy == uid`); менять и удалять может только автор; всем разрешено менять только `bc` и `updatedAt` (добавить штрих-код). После v102 правила нужно заново опубликовать.
- `barcodes` (v51) — читают все вошедшие; создавать может любой (id документа = код 6–20 символов, поля только `productId`, `createdBy`, `createdAt`, `createdBy == uid`); обновлять нельзя, **удалить может только добавивший**. После v51 правила нужно заново опубликовать в Firebase Console, иначе общие коды не сохранятся.

## 4. Вкладки и функции

Нижнее меню: **Дневник · Продукты · Здоровье · Отчёты · Я**.

### 4.1 Дневник
- Выбор даты (листание назад без ограничения), кольцевая диаграмма калорий и БЖУ («Белки», «Жиры», «Углеводы» — полными словами), серия дней подряд.
- **С v95** под неделей плашка «Сегодня тренировка» (или «Тренировка в этот день», «Тренировка выполнена») с названием, временем и прогрессом; нажатие открывает Здоровье → Тренировки.
- Четыре приёма пищи с карточками: калории и кнопка «+» выровнены по центру высоты.
- **Распределение цели по приёмам пищи (v26)**: у каждого приёма есть своя доля дневной цели (по умолчанию завтрак 30%, обед 35%, ужин 25%, перекус 10%; `MEAL_SPLIT_DEFAULT`). В карточке показано «съедено из N ккал» и полоска прогресса (`.meal-plan > .track`), которая заполняется по мере записи еды и краснеет при переборе. Проценты меняются во вкладке «Я» → «Дневная цель» (сохраняются в `settings/profile.mealSplit`, сумма приводится к 100 функцией `normalizeSplit`). Цель пересчитывается автоматически при смене калорий в день.
- **План и факт по БЖУ (v31)**: в карточке приёма пищи у белков, жиров и углеводов показано «факт из план». План приёма = суточная цель по БЖУ × доля приёма. Суточная цель БЖУ берётся из профиля (`goalProtein/goalFat/goalCarbs`) и пропорционально приводится к текущей цели по калориям. Если факт больше плана, значение выделяется только красным цветом, без жирного (также калории приёма и строки «Баланса БЖУ»); у всех значений БЖУ указаны граммы («Белки 12,3 г из 41 г»). Без профиля показывается только факт.
- Добавление еды: поиск по базе (не различает «е»/«ё», понимает несколько слов: «куриная жарен»), ввод граммов, мгновенный пересчёт КБЖУ.
- Главная формула: `значение на 100 г × граммы / 100`.
- Правка и удаление записей, цель по калориям.

### 4.2 Продукты
- Общая база: видят и добавляют все пользователи, у каждого продукта автор; править и удалять — только автор.
- Базовый набор (кнопка добавления): 129 позиций, у многих варианты «сырой / варёный / запечённый / жареный»; 15 супов и борщей с гидратацией 72–92%.
- Форма продукта: название, бренд, штрих-код, КБЖУ на 100 г, блок «Это напиток» (гидратация и кофеин на 100 мл) с полем-поиском «Похож на» (можно печатать, список фильтруется, тап подставляет гидратацию и кофеин).
- **Несколько штрих-кодов у продукта (v50–v51)**: в карточке продукта блок «Другие упаковки» (ввод, сканирование, удаление × у своих кодов). Коды общие для всех пользователей и хранятся в коллекции `barcodes`. При сканировании неизвестного кода приложение предлагает привязать его к существующему продукту (поиск по списку) или создать новый. Поиск по продуктам находит и по привязанным кодам.
- Защита от дубликатов штрих-кода (учитывает и привязанные коды); прежние личные продукты автоматически переносятся в общую базу при первом входе.

### 4.3 Сканер штрих-кодов
Порядок поиска: свой/общий список → Open Food Facts → ручной ввод (данные вводятся один раз, дальше продукт находится по коду).
- **Собственный декодер EAN-13 на чистом JS** (v10): адаптивный порог, строки скан-линий, таблицы L/G/паритет, контрольная цифра, поворот на 90° и код вверх ногами, устойчив к бликам. Проверен на реальном скриншоте пользователя.
- Дополнительно: системный `BarcodeDetector` (WASM, jsdelivr/fastly/unpkg) и ZXing-js как запасной.
- Кнопка «Сфотографировать код» (камера iPhone с автофокусом), несколько масштабов.
- Кнопка фонарика (`applyConstraints({advanced:[{torch}]})`) — на iOS Safari может не поддерживаться.
- Внизу окна строка диагностики (кадры, движок, ошибка).
- Поиск по названию в Open Food Facts по кнопке (лимит сервиса 10 запросов в минуту).
- Запрет масштабирования щипком и двойным касанием.

### 4.4 Здоровье
- **Профиль** (при первом входе знакомство): пол, возраст (18–80), рост, вес, уровень активности, цель — похудеть / набрать мышцы / удержать вес.
- **План** (`computePlan`): BMR по формуле Миффлина — Сан-Жеора; TDEE = BMR × коэффициент (1,2 / 1,375 / 1,55 / 1,725). Похудение: дефицит 20% TDEE, но 300–700 ккал, минимум 1500 (м) / 1200 (ж); при ИМТ < 18,5 цель «похудеть» заменяется на поддержание с предупреждением. Набор: +10% TDEE, но 200–400 ккал. Белок 2,0 / 1,8 / 1,6 г на кг; жиры не менее 0,8 г/кг и 25% калорий; остальное — углеводы. Вода: ≈33 мл на кг, диапазон 1500–4500 мл. Недельный ориентир нагрузки: 200 / 180 / 150 минут и 2–3 силовые.
- **Вода** (с v33 с историей): кнопки «+150/+250/+330/+500», «Другое», «−250» и выбор «Вода» в окне напитков каждый раз создают отдельную запись в `drinks` (`drinkId: "water"`, `name: "Вода"`, гидратация 100%, с временем), которая видна в списке «Жидкость» со временем. «−250» — тоже запись (с минусом), но не больше воды, записанной за день. Раньше вода прибавлялась к одной сумме за день (`water/{дата}`) без истории; старые суммы остаются в учёте и показываются строкой «записано суммой за день».
- **Напитки** (справочник из 106 позиций + «Свой напиток», категории, поиск, избранное и частые): засчитывается `объём × гидратация%` (у алкоголя процент отрицательный).
- **Напитки с калориями** (v17): у 86 из 106 есть ккал и БЖУ на 100 мл. Выбрали капучино — создаётся **одна** запись в дневнике (выбранный приём пищи), она же считается в жидкость и кофеин, повторно вносить не нужно. Напитки с нулевыми калориями (вода, чай, чёрный кофе, диетические) идут в коллекцию `drinks`.
- **Супы и борщи** (v18): считаются и как еда, и как жидкость одной записью (мл ≈ граммы). Скан упаковки супа/бульона распознаётся как «еда + жидкость».
- **Кофеин**: суточная норма по весу (EFSA) = `min(400, 5,7 × вес)` мг; разовая = `min(200, 3 × вес)` мг. Предупреждения: близко к норме (≥80%), превышение, большая порция, кофеин после 16:00.
- **Список «Жидкость» (v23)**: показываются 2 последних напитка (новые сверху), кнопка «Ещё N» раскрывает весь список, «Свернуть» возвращает; при смене дня сворачивается.
- **Нагрузки**: 11 видов с MET (ходьба, быстрая ходьба, бег 8 и 10 км/ч, велосипед, плавание, силовая, HIIT, йога, танцы, командные игры); расход считается из MET, веса и времени.
- Недельный прогресс, графики за неделю.
- **С v29 вкладка данных с часов** (подробности и настройка в разделе 11): карточка «Активность» (шаги с полосой до ориентира 8 000, активные ккал, средний пульс от и до, пульс в покое, шагов в день за неделю), карточка «Тренировки» (тренировки с Apple Watch и записи вручную, кнопка «+ Добавить»), график «Шаги за неделю». Минуты нагрузки дня = записи вручную + тренировки с часов; калории = вручную + большее из «активных ккал часов» и «ккал тренировок» (чтобы не считать дважды). Если одну прогулку записали и вручную, и часами, она посчитается дважды: лишнюю запись удалить.
- **С v30 силовые тренировки с часов**: тренировка считается силовой, если в названии есть «силов», «функциональн», «кроссфит», strength, functional или crossfit; у каждой тренировки есть кнопка «Отметить силовой» / «Силовая ✓», ручная отметка главнее названия и хранится в `workouts/{id}.strength` (Worker её не стирает). ### 4.5 Отчёты (аналитика)
- Периоды: 7 / 14 / 30 / 90 дней, «Год», «Всё» и «Свой» (выбор двух дат, можно любые даты с 2020-01-01 до сегодня). Всего 7 кнопок; на узком экране iPhone выглядит нормально (подтверждено).
- С v29 в итогах периода добавлены «шагов в день» и «пульс в покое», график «Шаги» (с пунктиром 8 000), тренировки с часов входят в «Нагрузки по видам»; ИИ получает шаги, пульс, число тренировок и силовых.
- Блоки: итоги периода, краткие выводы без ИИ (`localInsights`; **с v25 скрыты по умолчанию**: кнопки «Показать краткие выводы» / «Скрыть…», `state.insOpen`), БЖУ в день к плану, по приёмам пищи, по дням недели, что ем чаще всего, что пью (вода, напитки, кофеин, калории, алкоголь), нагрузки по видам.
- Периоды > 120 дней на графиках группируются по неделям; в Gemini уходит недельная сводка.
- **Кнопка «Проанализировать»**: собирает сводку периода (`aiPayload`) и отправляет в Gemini, результат показывается карточкой (простой markdown-рендер `mdLite`).
- **Последний ответ хранится до нового запуска (v24)**: в `localStorage` (`ai_last`) и в Firestore `users/{uid}/settings/ai`, поэтому виден на всех устройствах и при любом выбранном периоде. Под ответом указан период анализа и время получения. При ошибке прежний ответ остаётся на экране, заменяется только новым успешным.
- **Упражнения дома (v28)**: в промпт Gemini (`aiPrompt`) добавлен обязательный раздел «## Упражнения дома»: 4–6 упражнений без оборудования под цель, вес, возраст и текущую нагрузку (подходы, повторения, частота, техника), с ограничениями безопасности. Старый сохранённый анализ этого раздела не содержит: нужен новый запуск.
- **Удаление анализа (v27)**: кнопка «Удалить анализ» (`aiDelete`) очищает `localStorage.ai_last` и удаляет документ `settings/ai`; текст анализа отдвинут от кнопок на 18 px. Подтверждение не запрашивается.
- **Состояние запуска (v24)**: `state.ai` = `{busy, error, detail, step}`. Раньше кнопка, ожидание и ошибка жили в DOM и стирались любой перерисовкой из Firestore (причина «ничего не произошло»), а ошибка показывалась только тостом на 3 с. Теперь ход запроса («Подбираю модель…», «Запрос к … попытка N из M») и ошибка с деталью видны в карточке. У запросов таймаут: список моделей 20 с, генерация 40 с на попытку (`fetchT`).
- Ключ Gemini: с aistudio.google.com/apikey, вводится в листе настройки, хранится только в `localStorage` (`gemini_api_key`) **на каждом устройстве отдельно** (в аккаунт не синхронизируется), с устройства никуда, кроме Google, не уходит. Формат нового ключа `AQ.…` с точкой — проверка `/^[\w.~-]{20,}$/`.
- Выбор модели: ListModels, стабильные flash выше preview и lite, до 5 попыток; при ошибке 503 («высокий спрос») — повторы и переход на следующую модель, понятное сообщение по-русски.

### 4.6 Я
- Профиль, цель по калориям, выход, ключ Gemini («забыть ключ»).
- **Состояние в карточке аккаунта (v25)**: цветные индикаторы «Вход», «Интернет», «Сервер (Firestore): подключён / не подключён», «Правила Firestore: работают / блокируют доступ», «Версия приложения: актуальная / на сервере новее», «Синхронизация данных», «Gemini (ключ)» и кнопка «Проверить снова» (`checkStatus`, `statusHtml`). Сервер и правила проверяются чтением непосредственно с сервера (`getDocFromServer`: свой профиль; `getDocsFromServer` + `limit(1)`: общая база продуктов); `permission-denied` = правила не опубликованы или неверны, другая ошибка = нет связи. Права на запись не проверяются.

  `?add=water&ml=250`, `?add=water&ml=500`, `?open=food`, `?open=scan`, `?open=drink`, `?open=activity`, `?tab=health` (+ `meal=`, `tab=`). Параметры читаются один раз и удаляются из адреса.

## 11. Автоматическое подключение Apple Watch / Здоровья (Health Auto Export + Cloudflare Worker)

### 11.1 Зачем такая цепочка
Веб-приложение (PWA в Safari) **не имеет доступа к данным Здоровья**: у браузера нет HealthKit. Поэтому используется посредник:

```
Apple Watch → приложение «Здоровье» на iPhone → Health Auto Export (iPhone)
   → HTTPS POST с JSON → Cloudflare Worker «health-ingest»
   → Firestore (users/{uid}/health, users/{uid}/workouts) → приложение Health
```

Важно понимать направление: **iPhone сам отправляет данные**. Cloudflare и приложение ничего не запрашивают у телефона и не могут запросить.

### 11.2 Что понадобится
| Что | Зачем | Примечание |
|---|---|---|
| iPhone с Apple Watch, приложение «Здоровье» | источник данных | часы должны быть сопряжены, в «Здоровье» должны появляться шаги, пульс, тренировки |
| Приложение **Health Auto Export** (App Store) | выгружает данные Здоровья в JSON по HTTPS | автоматизация типа «REST API» может требовать платной подписки Premium (проверить в приложении) |
| Аккаунт **Cloudflare** (бесплатный) | хостинг Worker; бесплатно до 100 000 запросов в сутки | аккаунт на dash.cloudflare.com |
| Проект **Firebase** `calorie-app-45bd1` | база данных | уже есть |
| Вход в приложение Health через Google | чтобы появился ваш **UID** | войти хотя бы один раз |
| Файл `worker.js` | код Worker | лежит рядом с проектом; на GitHub не загружается |

### 11.3 Шаг 1. Узнать свой UID
1. Откройте приложение Health и войдите через Google (если ещё не входили).
2. Firebase Console → проект `calorie-app` → **Authentication** → вкладка **Users**.
3. В строке вашего аккаунта скопируйте **User UID** (длинная строка из букв и цифр). Он понадобится на шаге 4.
UID можно найти и в Firestore: Firestore Database → `users` → имя документа.

### 11.4 Шаг 2. Ключ сервисного аккаунта (даёт Worker право писать в базу)
1. Firebase Console → шестерёнка → **Project settings** → вкладка **Service accounts**.
2. Нажмите **Generate new private key** → **Generate key**. Скачается JSON-файл.
3. **Никому не показывайте файл, не вставляйте его в чат и не загружайте в репозиторий GitHub**: ключ даёт полный доступ к базе. Он нужен только в одном месте: как секрет в Cloudflare (шаг 4).
4. Если ключ случайно попал в чат, письмо или репозиторий, его надо отозвать: Google Cloud Console → проект `calorie-app-45bd1` → **IAM и администрирование → Сервисные аккаунты** → аккаунт `firebase-adminsdk-…` → вкладка **Ключи** → удалить скомпрометированный ключ → создать новый. (13.10.2026 ключ был вставлен в чат: убедиться, что тот ключ удалён, а в Cloudflare лежит новый.)

### 11.5 Шаг 3. Создать Worker в Cloudflare
1. dash.cloudflare.com → слева **Workers & Pages** → **Create** → **Create Worker**.
2. Имя: `health-ingest` → **Deploy** (сначала создастся заготовка «Hello World»).
3. Откройте **Edit code**, удалите весь код, вставьте целиком содержимое `worker.js` и нажмите **Deploy**.
4. Адрес Worker вида `https://health-ingest.<ваш-поддомен>.workers.dev` (виден на главной странице Worker и в Settings → Domains & Routes).
5. Проверка: откройте этот адрес в браузере. Должна появиться надпись **«health-ingest: работает»**.

### 11.6 Шаг 4. Секреты и переменные Worker
Worker → **Settings** → **Variables and Secrets** → **Add**. Создайте три записи, каждую отдельно (тип **Production**):

| Key (имя, в первом поле) | Value (значение, во втором поле) | Тип |
|---|---|---|
| `SERVICE_ACCOUNT` | весь JSON из скачанного ключа, от `{` до `}` | **Secret** |
| `INGEST_TOKEN` | длинная случайная строка (30+ символов, придумайте сами; запишите её, она нужна в Health Auto Export) | **Secret** |
| `FIREBASE_UID` | ваш UID из шага 1 | Variable (обычная) |

Частая ошибка: вставить JSON в поле **Key**. Тогда Cloudflare пишет «Variable name must start with a letter…». В Key идёт только имя (например `SERVICE_ACCOUNT`), в Value — содержимое. После добавления нажмите **Deploy**. Значения секретов дальше не видны: это нормально.

### 11.7 Шаг 5. Настроить Health Auto Export (две автоматизации)
Данные двух видов (показатели и тренировки) в одной автоматизации выгрузить нельзя: тип данных выбирается один на автоматизацию. Поэтому их две; обе шлют на один и тот же адрес Worker.

**Сначала разрешите приложению читать Здоровье:** при первом запуске iOS покажет окно доступа к данным: включите все нужные категории (Число шагов, Активная энергия, Пульс, Пульс в покое, Тренировки). Позже это меняется в: Здоровье → фото профиля → **Приложения** → Health Auto Export.

**Автоматизация 1 «Показатели»** (Автоматизации → **+** → новая автоматизация):
| Параметр | Значение |
|---|---|
| Название | Показатели |
| Тип автоматизации | **REST API** |
| URL | адрес Worker (`https://health-ingest.<поддомен>.workers.dev`) |
| Метод | POST |
| Заголовки (Add headers) | ключ `Authorization`, значение `Bearer <ваш INGEST_TOKEN>` (слово Bearer, пробел, токен) |
| Тип данных | **Показатели здоровья** |
| Выберите показатели | Число шагов, Активная энергия, Пульс, Пульс в покое (4 штуки) |
| Формат экспорта | JSON, версия **v2** |
| Диапазон дат | **Сегодня** (чтобы в каждой отправке был весь день: итоги дня пересчитываются целиком) |
| Частота синхронизации | 15 минут (меньше смысла не имеет: см. 11.8) |
| «Уведомлять при обновлении кэша» / «Уведомлять при запуске» | **выключить** |
| Включено | да |

**Автоматизация 2 «Тренировки»**: то же самое, но:
| Параметр | Значение |
|---|---|
| Название | Тренировки |
| Тип данных | **Тренировки** |
| Диапазон дат | **7 дней** (догонит тренировки, которые часы досылают позже; дублей не будет, потому что тренировка пишется по своему id) |
| Данные пульса тренировки | включить, если есть такая настройка |
| Маршрут (GPS) | выключить (файл становится огромным) |

**Ручная выгрузка для проверки** (в каждой автоматизации): прокрутите вниз до «Экспортировать существующие данные» → **Ручная загрузка** → выберите даты → **Начать экспорт**. В блоке «Ответ» должно быть:
- для «Показателей»: `ok: дней N, тренировок 0`
- для «Тренировок»: `ok: дней 0, тренировок N`
Чтобы подтянуть шаги за прошлые дни, один раз сделайте ручную выгрузку «Показателей» за 7 дней.

### 11.8 Шаг 6. Настройки iPhone, чтобы отправка шла сама
Фоновую отправку запускает iOS, а не Cloudflare. Что повышает шанс:
- Настройки → Основные → **Обновление контента** (Background App Refresh): включено глобально и для Health Auto Export.
- **Режим энергосбережения выключен** (при нём фон почти не работает).
- Приложение Health Auto Export **не закрывать смахиванием** в переключателе приложений.
- Разрешены мобильные данные для приложения (не только Wi-Fi).
- Помнить: данные Здоровья шифруются, пока телефон заблокирован; в фоне при заблокированном экране чтение может не сработать.
- Значение «каждые 5 или 15 минут» означает «не чаще». Реальные запуски решает iOS и они могут быть редкими.
Надёжный способ: на пару секунд открывать Health Auto Export перед просмотром статистики. Диагностика: в автоматизации **Смотреть журналы активности** (время попыток и ответы).
Запасной вариант: личная автоматизация в приложении «Команды» (Shortcuts), которая по времени или при зарядке открывает Health Auto Export; результат зависит от версии iOS.

### 11.9 Шаг 7. Проверить, что данные дошли
1. Firebase Console → Firestore Database → `users` → ваш UID: появились коллекции **`health`** (документы по датам ГГГГ-ММ-ДД) и **`workouts`**.
2. Приложение Health → вкладка **Здоровье**: карточка «Активность» (шаги, пульс, «Обновлено в …») и «Тренировки».
3. Полностью закрыть и открыть приложение, если вид старый; в «Я» должно быть «актуальная» версия.
4. Коллекцию `healthInbox` (сырые данные из первой версии Worker) можно удалить: она больше не используется.

### 11.10 Диагностика
| Что видно | Причина | Что делать |
|---|---|---|
| Ответ `401 unauthorized` | токен в заголовке не совпадает с `INGEST_TOKEN` | проверить `Authorization: Bearer <токен>`, пробелы, лишние символы |
| Ответ `500 worker not configured` | не заданы `SERVICE_ACCOUNT` или `FIREBASE_UID` | добавить в Worker, Deploy |
| Ответ `error: token …` | `SERVICE_ACCOUNT` вставлен не целиком или повреждён | вставить весь JSON заново в Value |
| Ответ `502 firestore 403/404` | сервисному аккаунту нет доступа или неверный проект | проверить ключ именно проекта `calorie-app-45bd1` |
| Ответ `400 bad json` | отправлен не JSON | в автоматизации формат JSON v2 |
| Ответ `ok`, но без «дней/тренировок» | старый код Worker | вставить актуальный `worker.js`, Deploy |
| Ответ `ok: нет данных для записи` | выбрана не та категория или пустой диапазон | проверить тип данных и выбранные показатели |
| В Firebase пусто, ответа нет | автоматизация не запускалась | ручная выгрузка; настройки iPhone (11.8) |
| В Firebase есть, в приложении «нет данных с часов» | нет документа за выбранную дату | полностью перезапустить приложение; выбрать день с данными |
| Cloudflare: «Variable name must start with a letter…» | JSON вставлен в поле Key | Key = имя, JSON = Value |
| Данные приходят только при открытии Health Auto Export | ограничение iOS на фон | 11.8 |

### 11.11 Что и как сохраняется (формат данных)
Исходный JSON Health Auto Export v2: `data.metrics[]` (`name`, `units`, `data[]` с полем `date` вида `ГГГГ-ММ-ДД ЧЧ:ММ:СС +0300`) и `data.workouts[]`. Worker разбирает его и **сырой JSON не хранит**:
- `health/{дата}` (день берётся из начала строки даты, то есть по местному времени телефона): `steps` (сумма за день, округлена; значения у шагов бывают дробные из-за объединения источников), `activeKcal` (активная энергия; приходит в **кДж**, переводится в ккал делением на 4,184), `hrAvg` (среднее значений пульса за день), `hrMin`, `hrMax`, `hrN` (число замеров), `restingHr` (последнее значение дня; может быть единичным замером, а не истинным пульсом покоя), `updatedAt`.
- `workouts/{id}` (id тренировки из Apple): `name` (на русском с часов, например «На улице Ходьба»), `date`, `start`, `end` (время; `end − start` может включать паузы), `minutes` (**активное** время `duration`, паузы не учитываются), `kcal` (из `activeEnergyBurned`, кДж → ккал), `distanceKm`, `hrAvg`, `hrMax`, `hrMin`, `indoor`, `updatedAt`, плюс `strength` (true/false) если вы нажали кнопку.
- Каждая отправка **перезаписывает** итог дня и тренировку по её id, поэтому повторные отправки не создают дублей. Для «Показателей» диапазон «Сегодня» обязателен: если отправится только кусок дня, итог дня окажется неполным.
- Размер: один документ дня около 1 КБ; бесплатные лимиты Firestore (20 000 записей и 50 000 чтений в сутки) не страдают.

### 11.12 Как определяется «силовая тренировка»
Название тренировки с часов проверяется на слова «силов», «функциональн», «кроссфит», strength, functional, crossfit. Не совпало (например «Интервальная тренировка высокой интенсивности», «Ходьба», «Бег») → не силовая; отметить можно вручную кнопкой в карточке тренировки. На часах для силовых лучше выбирать тип «Силовая тренировка», тогда ничего отмечать не придётся.

### 11.13 Безопасность
- Worker принимает запросы только с заголовком `Authorization: Bearer <INGEST_TOKEN>` (сравнение за постоянное время); без него ответ 401.
- Ключ сервисного аккаунта хранится только в секрете Cloudflare (после сохранения он не отображается). Никогда не коммитить его в GitHub и не пересылать.
- Правила Firestore для этих данных не менялись: коллекции лежат внутри `users/{uid}/…`, читает только владелец. Worker пишет с правами сервисного аккаунта и правила обходит, поэтому ему нужен отдельный секрет, а токен защищает вход.
- Токен и UID нигде не хранятся в репозитории: приложение GitHub Pages ничего об этой схеме не знает, оно только читает Firestore.

### 11.14 Подключение второго человека (не реализовано, предложено)
Каждый человек использует свой Google-вход (свой UID), свой iPhone с Health Auto Export и свой токен. Варианты: **A)** отдельный Worker на каждого (копия кода со своими `INGEST_TOKEN` и `FIREBASE_UID`; ключ `SERVICE_ACCOUNT` вставляется в каждый); **B)** один Worker, где по токену определяется UID (в переменной хранится соответствие токен → UID); код нужно изменить, текущий токен продолжит работать. Рекомендован вариант B.

### 11.15 Как восстановить схему с нуля
1. Удалить все секреты, убедиться, что старый ключ сервисного аккаунта отозван, создать новый ключ (11.4).
2. Вставить актуальный `worker.js` (11.5), заново задать три записи (11.6).
3. Проверить ручной выгрузкой (11.7) и в Firebase (11.9).

## 12. План домашних тренировок (v95)

### Что умеет
- Анкета (можно менять в любой момент): место (дома / на улице / в зале), дни недели (по умолчанию пн, ср, пт), время 15/20/30/45/60 мин, уровень, инвентарь по месту, ограничения (колени, спина, плечи, запястья).
- Инвентарь пользователя по умолчанию: коврик, трубчатые эспандеры с ручками, дверной якорь, длинные резиновые петли, беговая дорожка. Гантели можно добавить в анкете.
- План на неделю: три полноценные тренировки (A ноги и ягодицы, B спина и руки, C грудь, плечи и кор), разминка, кардио, растяжка. Время выбирается чипами прямо в плане.
- Разовый перенос тренировки на другой день («Перенести»), расписание анкеты не меняется.
- Плашка «Сегодня тренировка» в Дневнике.
- У каждого упражнения: схематичный рисунок (начало и конец, SVG), шаги, частые ошибки, кружок «выполнено».

### Данные
- `users/{uid}/settings/training` — анкета и разовые переносы (`moves`).
- `users/{uid}/trainlog/{ГГГГ-ММ-ДД}` — `{date, done:{"группа:упражнение":true}, minutes}`.
- В `workouts` / `activity` не пишется: статистика, отчёты и ИИ отметки не видят. Правила Firestore не менялись.

### Файлы
- Новый `train.js` (библиотека 34 упражнений, рисунки, построение плана), изменены `app.js` (v95), `style.css` (v73), `index.html`, `README.md`.
- Загрузка на GitHub: все файлы из архива `health-app-v95.zip`.

### Проверено / нет
- Проверено в безголовом Chromium с подменой Firebase: анкета, сохранение, план, отметки, окно упражнения, плашка в дневнике.

### Завершение тренировки и прогресс (v97)
- Кнопка «Завершить тренировку» под списком упражнений: самочувствие 1–5 (очень легко … очень тяжело), использованный инвентарь, резинки по цветам (жёлтая, красная, синяя, зелёная, чёрная; несколько сразу) с весом в кг, вес гантелей. Вес по цвету запоминается (`bandKg`). Итоги можно изменить.
- Карточка «Прогресс тренировок» (`trainStats`): за последние 6 недель (с даты начала) считает упражнения выполнено/запланировано (план берётся из снимка `plan` в день завершения, иначе пересобирается), завершённые тренировки, серию без пропусков, среднее самочувствие, выполнение по неделям, выполнение по каждому упражнению внутри групп мышц, список «чаще всего пропускаете», последние тренировки с резинками и весом.
- Адаптация (v97, расширена в v126): см. `trainAdvice`; на прошедшие дни не влияет.
- «Сбросить весь прогресс» удаляет все документы `trainlog` (с подтверждением); анкета и расписание остаются.
- Подписка `trainlog` теперь за 400 дней. Прогресс по упражнению считается только по основной части.
- Отчёты (v98): карточка «Тренировки по плану» после блока «Вес» на вкладке «Общее», учитывает выбранный период; использует `trainStats(from, to)`. Тренировки плана не входят в «нагрузки по видам», шаги, пульс и счётчик силовых (они только из Apple Health и ручных записей).
- ИИ и выводы (v99): `trainPlanData(from, to)` даёт данные плана за период; в Gemini они идут отдельным ключом и помечены как не относящиеся к Apple Health. Раньше (v95–v98) отметки плана в ИИ не передавались; теперь передаются по просьбе пользователя (16.10.2026), но общая статистика нагрузок по-прежнему их не включает.
- Резинки (v100): на трубках пользователя нет маркировки веса, продавец неизвестен; значения по цветам взяты из типового набора «до 100 фунтов» (порядок жёлтая, красная, синяя, зелёная, чёрная как назвал пользователь) и помечены в окне как «ориентир». У другого продавца цвета могут соответствовать другому весу.
